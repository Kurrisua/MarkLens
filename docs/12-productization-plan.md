# MarkLens 产品化重构计划（审核版）

> 状态：**已批准并完成首轮实施（2026-07-20）**
> 目标：将当前教学 MVP 重构为面向普通用户的“商标学习与品牌保护助手”，并提供严格隔离的运营后台。
> 非法律声明：系统仍仅提供初筛、学习与辅助材料，不构成法律意见，也不替代官方数据库、行政机关或律师审查。

## 1. 现状与重构原因

当前系统已具备多模态检索、风险评分、法律 RAG、报告初稿和数据源同步能力，但仍是一个开发/教学工作台：

- 没有账号、会话、角色或资源归属；任何调用方都能读取全部案件及文书；
- 用户端导航中包含数据源同步，工作台直接呈现 MySQL、模型和数据版本等内部信息；
- 所有接口混在 `/api/v1/*` 下，无法从服务端区分用户能力与运营能力；
- 没有品牌项目、方案版本、学习内容、案例或实训任务等面向用户的产品对象；
- `AgentRun` 的内部阶段、运行编号和底层错误直接暴露给终端用户。

本次重构以“真正的产品边界”为原则：**前端隐藏不是安全措施；每项用户资源都必须在后端按当前用户校验归属，所有运维 API 都必须在后端校验角色。**

## 2. 产品定位与用户

### 2.1 产品定位

MarkLens 是面向商标初学者、创业团队和课程实训的品牌保护助手，帮助用户完成商标知识学习、类别规划、近似初筛、风险理解、报告保存与学习实训。

### 2.2 三类角色

| 角色 | 目标 | 可访问范围 |
|---|---|---|
| `user` | 学习、创建自己的品牌项目并完成风险初筛 | 仅自己拥有或被授权协作的项目、资产、分析、报告和学习记录 |
| `operator` | 维护面向用户的内容与演示数据 | 内容、案例、题库、实训任务、数据同步任务、基础运营统计 |
| `admin` | 管理平台安全与运营 | 所有运维能力、用户与角色、审计日志、系统诊断与配置 |

首期不做复杂企业多租户和付费体系；保留 `ProjectMembership` 结构，为后续“项目协作成员”留出扩展空间。

## 3. 信息架构

### 3.1 用户端（`/`）

| 区域 | 页面/路由 | 用户价值 |
|---|---|---|
| 公开首页 | `/` | 说明产品能力、合规边界和主要行动入口；未登录可浏览科普与示例 |
| 学习中心 | `/learn`、`/learn/topics/:slug` | 商标基础知识、注册流程、概念关系、常见误区与法规引用 |
| 案例实训 | `/practice`、`/practice/:id` | “你来当审查员”判断题、案例解析、得分与学习记录 |
| 品牌项目 | `/projects`、`/projects/new`、`/projects/:id` | 一个品牌/业务一个项目，集中保存方案、分析、报告和笔记 |
| 新建方案 | `/projects/:id/marks/new` | 填写名称、业务描述、类别与图样；完成名称体检和类别确认 |
| 分析结果 | `/projects/:id/marks/:id/search`、`.../risk` | 展示候选、证据、风险解读与修改方向，不泄露系统配置或内部运行信息 |
| 报告 | `/projects/:id/reports/:id` | 编辑、验证、下载报告；持续展示人工复核及免责声明 |
| 我的空间 | `/me`、`/me/history`、`/me/learning` | 项目、分析历史、收藏、学习进度和账号设置 |
| 身份 | `/login`、`/register` | 注册、登录、退出和找回密码（找回可作为后续迭代） |

用户端首页不再显示数据库/模型健康状态、数据源数量、法律资料内部版本、原始 AgentRun 编号或导入审计。

### 3.2 运维端（`/ops`）

运维端使用独立布局、独立导航与角色守卫；普通用户访问时返回 403 页面，不可仅依赖前端重定向。

| 模块 | 路由示例 | 责任 |
|---|---|---|
| 运营总览 | `/ops` | 用户量、项目量、任务成功率、内容发布状态、数据更新时间 |
| 内容中心 | `/ops/content` | 知识文章、主题、流程节点、常见问题发布与下架 |
| 案例与题库 | `/ops/practice` | 案例、判断题、参考解析、难度和发布状态维护 |
| 数据中心 | `/ops/sources`、`/ops/ingestions/:id` | 数据源状态、同步、失败记录、许可和追溯信息 |
| 知识库 | `/ops/legal-sources` | 法律资料、版本、生效期、切片/引用完整性管理 |
| 运营任务 | `/ops/runs` | 聚合查看异步任务、失败原因和重试入口 |
| 用户与角色 | `/ops/users` | 管理员管理用户状态和角色；运营仅只读脱敏概览 |
| 审计与诊断 | `/ops/audit`、`/ops/system` | 高敏感操作审计、内部依赖健康、配置版本；仅管理员 |

## 4. 页面与体验原则

### 4.1 用户流程

```text
学习商标知识 / 登录
        ↓
创建品牌项目 → 新建候选商标方案 → 类别与名称体检
        ↓
上传图样（可选） → 相似检索 → 风险解读 / 名称修改
        ↓
保存方案、生成报告、继续迭代或进入案例实训
```

### 4.2 终端用户可见的信息

- 使用“正在分析文字、读音与类别关联”等业务语言展示进度；
- 将可恢复的内部错误映射为友好说明，并提供重试；
- 报告展示引用、证据充分度、限制和人工复核提示；
- 明确演示数据或真实数据的范围，避免暗示穷尽检索；
- 允许用户删除自己的项目及上传图样，说明保留规则。

### 4.3 仅运维端可见的信息

- 数据库、模型、服务健康和原始错误细节；
- 数据源域名、限速、同步参数、失败原始记录；
- Prompt/模型/索引配置版本和 AgentRun 内部阶段；
- 全局用户、全量案件及审计日志；
- 内容发布与法律资料生效配置。

## 5. 后端与安全架构

### 5.1 API 分域

| 前缀 | 访问者 | 说明 |
|---|---|---|
| `/api/v1/auth/*` | 匿名/已登录用户 | 注册、登录、刷新、登出、当前用户 |
| `/api/v1/app/*` | `user`、`operator`、`admin` | 用户产品资源；所有资源按 owner/membership 校验 |
| `/api/v1/ops/*` | `operator`、`admin` | 运营内容、数据和任务；细分角色权限 |
| `/api/v1/admin/*` | `admin` | 用户角色、审计、系统诊断等高敏感操作 |
| `/health` | 部署监控 | 生产环境仅部署层或管理员网络可访问；不得作为用户页面数据源 |

现有 `/api/v1/*` 作为迁移期兼容层处理：先引入新接口并迁移前端，随后在一次明确的版本升级中删除旧接口，避免长期保留无授权入口。

### 5.2 认证方案

首期采用邮箱 + 密码认证：

- 密码使用 Argon2id 哈希，绝不保存明文；
- 短期 access token 放在内存，长效 refresh token 存 `HttpOnly`、`Secure`、`SameSite=Lax` Cookie；
- refresh token 数据库存储不可逆哈希，支持吊销、过期和设备会话管理；
- 登录、注册、上传和模型任务实施速率限制；
- CORS 改为白名单 origin + `allow_credentials=True`，配合 CSRF 校验保护 Cookie 写操作；
- 开发环境提供明确的“演示管理员初始化”命令，禁止在请求参数中自行声明角色。

如课程明确要求第三方登录或学校统一认证，可替换认证提供者，但资源授权模型不变。

### 5.3 授权不变量

1. `user` 无法读取、修改、下载或触发其他用户的任何项目资产与衍生资源；
2. `operator` 无法管理角色、查看密码/令牌或访问全量隐私内容；
3. `admin` 操作均写入不可更改的审计事件；
4. 所有资源查询均从当前认证主体和资源链路推导权限，不能只根据前端传来的 ID；
5. 图像内容下载必须校验图片所属项目或候选方案；
6. 运维接口缺少或角色不符的令牌一律返回 401/403，不能返回部分数据。

### 5.4 错误与日志

- 用户 API 返回稳定的业务错误码和本次可重试信息，不返回 Python 异常类型、模型配置或内部路径；
- 请求 ID 仅在失败帮助页以简化形式展示；原始关联信息仅在运维审计中可查；
- 审计事件记录 actor、动作、资源类型/ID、结果、时间与请求 ID，严禁记录密码、令牌和原图；
- `AgentRun` 关联 `owner_id` 与可见性，用户只获得简化任务视图，运维端获得受权的详细视图。

## 6. 数据模型与迁移方案

### 6.1 新增核心表

| 实体 | 关键字段 | 用途 |
|---|---|---|
| `users` | `id`、`email`、`password_hash`、`display_name`、`status` | 用户身份 |
| `user_roles` | `user_id`、`role` | 支持一个用户多角色，首期角色为 user/operator/admin |
| `auth_sessions` | `user_id`、`token_hash`、`expires_at`、`revoked_at` | 可吊销刷新会话 |
| `projects` | `owner_id`、`name`、`business_description`、`status` | 品牌项目容器 |
| `project_memberships` | `project_id`、`user_id`、`permission` | 为后续项目协作预留 |
| `mark_candidates` | `project_id`、名称、类别、图样、状态、版本 | 一项品牌中的多个候选商标方案 |
| `learning_topics` / `learning_articles` | 标题、内容、发布状态、排序 | 商标科普内容 |
| `practice_cases` / `practice_questions` | 题干、选项、答案、解析、难度、发布状态 | 案例与实训内容 |
| `learning_attempts` | `user_id`、题目、答案、结果、时间 | 学习记录 |
| `audit_events` | actor、动作、资源、前后摘要、request_id | 管理操作追溯 |

### 6.2 对现有表的改造

| 现有实体 | 改造 |
|---|---|
| `ImageAsset` | 增加 `owner_id`、`project_id`、`deleted_at`；下载接口做属主验证 |
| `CaseRecord` | 迁移为或关联到 `mark_candidates`，增加 `owner_id`、`project_id`；保留事实快照 |
| `SearchRecord`、`RiskAnalysis`、`DocumentDraft`、`Consultation` | 增加 `owner_id`，或通过候选/项目链路确定 owner；建立索引以保证按用户查询 |
| `AgentRun` | 增加 `owner_id`、`visibility`；拆分用户任务视图与运维任务视图 |
| `SourceDefinition`、`IngestionRun`、`Trademark`、`LegalSource` | 继续为平台级运营资产；只允许相应运维角色访问管理 API |

### 6.3 迁移策略

1. 新增身份、项目、审计和内容表；不删除既有数据；
2. 创建一个迁移管理员和一个“历史演示项目”归档账户；
3. 将已有案例、资产、检索、分析、报告和咨询记录归属给该账户/项目；
4. 为所有资源补齐非空 owner/project 外键及索引；
5. 引入授权测试后再迁移前端到新 API；
6. 确认无前端依赖后废弃旧的无鉴权 API。

实际执行迁移前必须备份数据库，并在副本库验证记录数、外键完整性和资源链路一致性。

## 7. 功能实施范围

### 7.1 第一版必须交付（MVP-Product）

- 身份认证、三角色、后端资源授权与审计；
- 用户端产品壳：首页、登录、项目列表/详情、我的空间；
- 将现有“新建分析 → 检索 → 风险 → 报告”迁入一个用户私有项目；
- 现有数据源、同步、系统健康、运行详情迁入 `/ops`；
- 运维端的运营总览、数据源同步、任务详情和用户角色管理；
- 基础学习中心：主题、文章、注册流程和至少一组互动判断题；
- 用户与运维端的空状态、错误状态、无权限页面、免责声明和演示数据提示；
- 回归现有多模态检索、风险评分、引用校验和文书编辑能力。

### 7.2 第二版增强（在第一版验收后）

- 名称体检、类别推荐和多个候选名称对比；
- 收藏/排除候选、风险变化对比、报告 PDF/Word 导出；
- 案例库、错题本、学习进度和综合实训任务；
- 项目协作成员邀请；
- 内容审批工作流、数据质量看板和受控任务重试。

### 7.3 明确不在本轮实现

- 真实官方/商业商标数据库抓取或绕过访问限制；
- 自动递交商标申请、作出确定法律结论或代替律师；
- 付费、订单、短信、企业 SSO、复杂多租户计费；
- 高并发生产基础设施与大规模实时监控。

## 8. 分阶段实施与验收

### P0：产品与接口契约定稿

**工作**：确认本计划、页面文案、角色矩阵、迁移边界；将 OpenAPI 按 auth/app/ops/admin 分域并补充错误码。

**验收**：产品路由图、角色权限矩阵、数据迁移清单和 API 契约通过审核；所有旧接口的替代接口都有映射。

### P1：身份与授权底座

**工作**：实现 users/roles/sessions/audit 表、认证、密码安全、依赖注入、资源归属和授权中间层。

**验收**：

- 未登录访问私有资源为 401；普通用户访问其他用户资源或 ops/admin 为 403；
- operator/admin 可按矩阵访问运维资源；
- 资产内容下载完成归属校验；
- 认证、越权、令牌吊销、审计均有自动化测试；
- 现有记录安全迁移到历史演示账户。

### P2：后端 API 分域与存量能力迁移

**工作**：新增 `/api/v1/app/*` 和 `/api/v1/ops/*` 接口，将检索链路接入 project/candidate/owner，分离任务视图，逐步停用旧无鉴权接口。

**验收**：用户完成一次完整分析与报告流程；用户响应无内部模型/数据源细节；运维同步任务仍可追踪；旧 API 已无公开无授权写入口。

### P3：用户端产品化重构

**工作**：重构公共首页、身份页面、产品导航、我的项目、候选方案及结果页面；移除用户端数据源和依赖健康页面；实现统一的进度、错误、空状态和无权限页。

**验收**：新用户无需理解 MySQL、模型、AgentRun 或数据源即可完成项目创建、检索、风险分析、报告保存；所有链接与刷新回到正确的用户上下文。

### P4：运营后台

**工作**：独立 `/ops` 布局，迁移数据源/导入页，增加总览、运行监控、用户角色管理、审计与系统诊断。

**验收**：operator 不得访问管理员模块；admin 能追溯角色和同步操作；用户端无法导航或请求运维数据。

### P5：学习与实训闭环

**工作**：发布学习主题、文章、流程时间线、案例题库、答题记录和成绩反馈；运营端支持发布和下架内容。

**验收**：用户可完成一次学习/答题并在“我的学习”查看记录；未发布内容不对用户可见；内容变更有审计记录。

### P6：质量、演示与交付

**工作**：端到端权限与关键旅程测试、响应式检查、可访问性基础检查、数据演示脚本、部署说明和答辩演示材料。

**验收**：干净环境能创建演示管理员和演示用户；两种角色完成各自流程；安全回归和既有检索/RAG 测试通过；文档明确数据边界与系统限制。

## 9. 测试与质量门槛

| 层级 | 必测内容 |
|---|---|
| 单元测试 | 密码哈希、令牌、角色判断、owner 链路、错误脱敏、题目计分 |
| API 集成测试 | 401/403、跨用户 ID 枚举、资产下载、ops/admin 授权、令牌吊销、审计写入 |
| 回归测试 | 检索、风险、RAG 引用、报告验证、数据源同步不退化 |
| 端到端测试 | 用户注册→项目→分析→报告；operator 同步/发布内容；admin 管理角色 |
| 手动验收 | 手机/桌面布局、空状态、加载状态、错误提示、免责声明、键盘可用性 |

最低安全门槛：不允许以“前端未展示”为理由跳过任何一项 API 授权测试。

## 10. 主要风险与决策点

| 决策/风险 | 计划处理方式 | 审核时需确认 |
|---|---|---|
| 认证复杂度 | 先做本地邮箱密码和安全会话，预留外部身份提供商适配层 | 是否接受首期不接学校 SSO/短信 |
| 存量无 owner 数据 | 归档进历史演示账户，保留可追溯迁移日志 | 是否需要保留现有案例可见性 |
| 课程周期 | P1–P4 构成可独立答辩的完整产品，P5 后续递进 | 优先级与最终截止日期 |
| 内容质量 | 明确真实/合成标识，所有法律内容可定位来源 | 是否有老师提供的指定内容/案例 |
| 运营权限 | 首期固定三角色，避免过度设计 | operator 是否应能查看用户分析的匿名统计 |

## 11. 推荐的首个可演示版本

答辩时可用两个账号展示同一套系统：

1. 演示用户：学习“商标近似”知识 → 创建“智能手表”品牌项目 → 输入两个候选商标 → 运行检索和风险分析 → 保存带引用的报告；
